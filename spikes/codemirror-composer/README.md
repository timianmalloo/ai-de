# Spike — can CodeMirror 6 serve the composer (A5) and the Source viewer (A6.2), inside WebView2, without React, at a build cost this repo should accept?

**Precondition.** R15 (the composer) may not depend on CodeMirror 6 until this spike answers.
Owner already established (not this spike's job to re-check): the repo has no root
`package.json` / `package-lock.json` and names neither React nor CodeMirror anywhere — re-verified
here (`git log --all` on both filenames across the whole history, zero hits at any commit), which
confirms the premise is correctly stated as absent, not merely stale. React is refused per Owner
condition (c) and was not evaluated. `npm` itself is present as a global tool (`npm -v` -> 12.0.2)
but this repo had never had an npm footprint before this spike created one, scoped to
`spikes/codemirror-composer/`.

## Answer: YES, with a named cost

CodeMirror 6 works without React, headless (Node+jsdom) and in a real Chromium engine (Edge 152,
the same engine family WebView2 embeds), covers every composer and Source-viewer requirement in
A5/A6.2, and can run without a bundler — but only by hand- or script-maintaining a 51-entry browser
import map, and only if the WebView2 host serves app assets over a virtual https:// origin
(`SetVirtualHostNameToFolderMapping`) rather than `NavigateToString`, which is what the existing
`spikes/webview2-airspace` host currently uses. That host change is real, standard, and not yet
built.

## Method

Two levels of execution, both against the same `lib.mjs` (framework-agnostic, zero React imports):

1. Headless, Node + jsdom (`test.mjs`) — mounts a composer `EditorView` and a read-only source
   `EditorView` into a jsdom document, using CodeMirror 6's real npm packages resolved by Node's
   native ESM loader (no bundler in this path either — Node resolves bare specifiers itself).
2. Real Chromium, no bundler (`browser-test.html` + `importmap.json`, generated by
   `gen-importmap.mjs`) — a plain `<script type="importmap">` mapping every `@codemirror/*`,
   `@lezer/*`, `@marijn/find-cluster-break`, `style-mod`, `w3c-keyname`, `crelt` and `codemirror`
   bare specifier straight to its file in `node_modules`, served over a local static HTTP server
   (import maps + bare specifiers do not resolve over `file://`), loaded with real
   `msedge.exe --headless=new` (Edge 152.0.4191.66, installed on this machine — the same Chromium
   build family the WebView2 runtime here also reports).

### Reproduce

```
cd spikes/codemirror-composer
npm install                       # installs the 4 direct deps + jsdom (52 CM6 packages total)
node test.mjs                     # headless jsdom proof: prints dom snippets + assertions
node gen-importmap.mjs            # regenerates importmap.json from node_modules exports
# serve this directory over http (any static server on port 8791), then:
"C:/Program Files (x86)/Microsoft/Edge/Application/msedge.exe" \
  --headless=new --disable-gpu --no-sandbox --virtual-time-budget=6000 \
  --dump-dom http://localhost:8791/browser-test.html > browser-dump.html
grep -o "<pre id=\"out\">.*</pre>" browser-dump.html   # the captured result, see below
```

`browser-dump.html` and `console.log` in this directory are the captured artifacts from the run on
2026-09-09 (Node v24.18.0, npm 12.0.2, Edge 152.0.4191.66, Windows 11).

## Observed

- jsdom run (`test.mjs`): both `EditorView`s constructed and threw no error once
  `MutationObserver`, a `ResizeObserver` stub and `navigator` (via `defineProperty`, since Node 24
  makes the global read-only) were supplied. `EditorView.measure` throws
  `ReferenceError: Window is not defined` on later async animation-frame ticks after the process's
  own teardown — a jsdom lifecycle artifact after the assertions already ran, not a mount failure.
- Real-Chromium run (`browser-test.html` via import map, no bundler): identical structural result
  to jsdom, in an actual browser engine:
  - Composer `contenteditable="true"`, `data-language="markdown"`.
  - `# Title` gets a heading token class; `**bold**` / `*italic*` get distinct highlight classes on
    both the marks and the content.
  - `@design-doc` is replaced by `<span class="cm-mention-chip" contenteditable="false"
    data-mention="design-doc">@design-doc</span>` flanked by `<img class="cm-widgetBuffer">`
    markers — a real widget that replaces the source text, not styled text (`Decoration.replace`
    with a `WidgetType`, confirmed by DOM inspection).
  - Fenced ` ```js ` block: the fence markers tokenize immediately; the JavaScript content inside
    the fence (`function hi() { return 1; }`) is unhighlighted for the first ~500ms because
    `@codemirror/lang-markdown`'s nested-language load (`LanguageDescription.load()` via
    `@codemirror/language-data`) and CM's background `ParseWorker` are asynchronous
    (`requestIdleCallback`, falling back to `setTimeout(..., 500)` when `requestIdleCallback` is
    undefined, as in Node). After that tick, the fence content carries the same token classes
    (keyword / identifier / number) as the standalone JS source view — nested highlighting works,
    but is not synchronous on first paint.
  - Source viewer: `contenteditable="false"`, `aria-readonly="true"`, `data-language="javascript"`,
    full keyword/identifier/number token classes present — read-only is
    `EditorState.readOnly.of(true)` + `EditorView.editable.of(false)`, both first-class, documented
    CM6 facets, not a hack.
  - The import map needed a package not in `@codemirror/*` or `@lezer/*`:
    `@marijn/find-cluster-break` (a transitive dependency of `@codemirror/state`). Missing it
    produced a hard, page-halting error: `Failed to resolve module specifier
    "@marijn/find-cluster-break"`. This is the concrete shape of the "no bundler" risk: the import
    map is a second dependency manifest that must be kept in sync by hand or by the generator
    script, and a future minor version bump that adds one more transitive package silently breaks
    the page with no build-time warning — only a runtime console error.

## Decision answer

YES, CodeMirror 6 can serve both surfaces, inside a Chromium engine, without React — but "at a
build cost this repo should accept" is UNCLEAR, not yes. The strongest evidence: the real-Chromium
run (`browser-dump.html`) rendering markdown, a highlighted fence, a genuine widget chip, and a
read-only highlighted source view, all from unbundled ES modules plus one hand-written import map —
proving the editor itself has no bundler dependency. The reason it doesn't clear to an unqualified
YES: the hosting integration does — the current WebView2 host (`NavigateToString`) cannot serve
import-map ES modules at all, so some change is mandatory before R15 can ship: either (a) adopt
`SetVirtualHostNameToFolderMapping` and keep `gen-importmap.mjs` as a maintained script (no new
toolchain, but a hand-rolled one), or (b) accept a minimal bundler (esbuild, single file output, no
config) and remove the import-map maintenance burden entirely.

What would have to be true for the opposite answer (NO): if `SetVirtualHostNameToFolderMapping`
turns out to be unavailable or disallowed in this repo's WebView2 hosting model (not checked here —
that host code is in a different worktree per this task's constraint), unbundled CM6 has no path
into the existing shell at all, and a bundler stops being optional.

Cheapest alternative if the answer settles to NO: vendor a single pre-built ESM bundle of CM6
(community CDN bundlers such as esm.sh can produce one on the fly) fetched once and committed —
avoids both a bundler and the import-map maintenance burden, at the cost of one large generated file
that must be manually refreshed on upgrade.

## Residual risks — flagged, not closed

1. WebView2 hosting change not built or tested. This spike proved CM6 runs unbundled in Edge 152
   (Chromium) served over plain HTTP. It did not run inside an actual WebView2Control /
   CoreWebView2 host, and did not implement or test SetVirtualHostNameToFolderMapping. That is the
   next probe, and it touches the WebView2 host code, which is in a different worktree per this
   task's constraint (another agent owns it).
2. IME/clipboard/focus parity inside WebView2 is genuinely unchecked (Q5). Cheapest next probe:
   drive the composer's EditorView inside the real webview2-airspace / webview2-snapshot-swap host
   and type IME (e.g., Japanese) input and paste rich-text clipboard content.
3. Async fence highlighting. The nested-language token classes for a fenced code block do not
   appear on first paint — CM6's ParseWorker needs an idle tick (roughly 100-500ms,
   requestIdleCallback or its setTimeout fallback). Not a defect, but a UX detail: content will
   visibly "pop" from plain to highlighted a moment after the fence is typed or the doc loads.
4. HTTP/2 vs. 52 separate file requests — not measured. If the virtual-host mapping serves over
   HTTP/1.1 without multiplexing, 52 module fetches per composer load may be a real latency cost on
   a slow machine; a bundler removes this by construction.
5. @codemirror/language-data's footprint pulls in language support (Angular, Go, Rust, PHP, SQL,
   YAML, ...) that R15 does not need — none of it is a runtime dependency of the rendered surface
   unless the markdown fence names that language, but it does add to the 52-package/11MB count. A
   narrower codeLanguages list (hand-picking only the languages the composer actually needs) would
   shrink both the dependency count and the import map.
6. Package-count claim is for this specific import set (markdown + one nested language +
   language-data's language catalog). A composer needing more embedded languages will pull in more
   @lezer/* parser packages; the count is not a fixed ceiling.

## Trimmed (Ruling 24 — cut `@codemirror/language-data`, re-measure)

**What was cut.** `package.json`'s dependency on `@codemirror/language-data` (which hard-imports
~20 language packages as a catalog) is replaced by a hand-picked `codeLanguages` array passed to
`markdown({ codeLanguages })` in `lib.mjs`, built with `LanguageDescription.of(...)` in the exact
shape `@codemirror/language-data`'s own source uses (verified by reading
`node_modules/@codemirror/language-data/dist/index.js` before writing the replacement). Three
languages, chosen for what a user of *this* repo would actually paste into a fence: **C#** (this
repo's own source language; loaded via `@codemirror/legacy-modes/mode/clike`'s `csharp` stream
parser — CodeMirror 6 has no dedicated `@lezer/csharp` grammar, `language-data` uses the same
legacy mode), **JSON** (config/data snippets; `@codemirror/lang-json`), and **Markdown itself**
(quoted/nested markdown; `@codemirror/lang-markdown`, already a direct dependency for the composer
language itself). `package.json` now declares `@codemirror/lang-json`, `@codemirror/language`
(imported directly for `LanguageDescription`/`LanguageSupport`/`StreamLanguage`, previously only a
transitive dependency) and `@codemirror/legacy-modes` in place of `@codemirror/language-data`.

**Before / after** (measured this session; before re-verified by a clean `npm install` against the
un-trimmed `package.json`, after by a clean reinstall against the trimmed one — `npm ls --all
--omit=dev --json` for package identity, `du -ch` over those package directories for disk size):

| Metric | Before | After | Change |
|---|---|---|---|
| Production (CM6) packages | 52 | 26 | −50% |
| Production packages, disk size | 11 MB | 7.5 MB | −32% |
| Full `node_modules` (incl. `jsdom` dev dep) | 90 packages, 37 MB | 64 packages, 34 MB | −29% packages, −8% size |
| Generated import-map entries (`importmap.json`) | 51 | 24 | −53% |
| Live import map (`browser-test.html`, incl. hand-added `@marijn/find-cluster-break`) | 52 | 25 | −52% |

Two things keep the reduction from being a clean 20-language-to-3: (a) `@codemirror/lang-markdown`
itself hard-depends on `@codemirror/lang-html` (→ `@codemirror/lang-css`) for embedded-HTML support
inside markdown — verified by reading `node_modules/@codemirror/lang-markdown/package.json`'s
`dependencies` — so those two packages stay regardless of the `codeLanguages` list; (b)
`@codemirror/legacy-modes`, needed only for the C# stream parser, ships as one package containing
*every* legacy-mode language (2.5 MB on disk by itself, the single largest addition) — the
unbundled import map only ever fetches its one `mode/clike.js` file at runtime, but the npm
package-count and disk-size metrics both count the whole package once it is a dependency at all.
Dropping C# from the list (JSON + Markdown only) would remove that 2.5 MB and both `@codemirror/
legacy-modes` and `@marijn/find-cluster-break`'s only remaining pull-in reason; it was kept because
C# is this repo's own source language and the more honest choice for what gets pasted into a
fence here.

**Still works — reverified, not assumed.** The MIME-type note: the original reproduce steps say
"any static server"; Python's `http.server` on this machine serves `.mjs` as `text/plain`
(`mimetypes.guess_type('x.mjs')` → `('text/plain', None)`, checked directly), which real Chromium's
strict module-script MIME checking rejects (`Failed to load module script: ... MIME type of
"text/plain"`, caught via `--enable-logging=stderr`). The reproduction needs a server that serves
`.mjs`/`.js` as `text/javascript`; a two-line Node `http` server suffices (not committed — it is a
throwaway dev-time tool, not part of the app or its build path).

Re-ran both proofs against the trimmed `lib.mjs`, with the composer fixture now mixing a **kept**
language (JSON) and an **unlisted** one (JS, since `javascript` is no longer in `codeLanguages`):
- `node test.mjs` (headless jsdom): composer mounts, `data-language="markdown"`,
  `contenteditable="true"`; mention chip present (`cm-mention-chip`, `data-mention="design-doc"`,
  flanked by `cm-widgetBuffer` markers — genuine `Decoration.replace` widget, not styled text);
  heading/bold/italic get distinct highlight classes; source viewer mounts read-only
  (`contenteditable` attr `"false"`, `data-language="javascript"`) with full keyword/identifier/
  number token classes.
- Real Chromium (`msedge.exe --headless=new --dump-dom` against `browser-test.html` over the
  MIME-correct server) — `browser-dump.html` in this directory is the captured artifact from this
  run: identical structural result — chip widget intact, heading/bold/italic highlighted, source
  viewer read-only and highlighted.
- **Kept-language fence (JSON):** `{ "hi": <span class="ͼd">1</span> }` — the numeric literal
  carries a highlight class in both runs, confirming `@codemirror/lang-json` loaded and tokenized.
- **Unlisted-language fence (JS):** `function hi() { return 1; }` — zero highlight spans, in both
  the jsdom and real-Chromium runs. Observed, not assumed: a fence naming a language outside the
  hand-picked `codeLanguages` list renders as **plain, unhighlighted text** (the fence markers
  ` ``` ` and the language tag `js` still get their own token classes from the outer Markdown
  grammar; only the fenced content itself stays unstyled). It does not error and does not block
  editing — CodeMirror falls back silently to no nested language.

**The vendored ESM bundle (Owner's option c).** Built once, from the packages the committed
`package-lock.json` resolves (never fetched from a CDN at runtime):

```

one-off recorded command whose output is committed — `npm`/`npx` is not wired into `AiDe.App`'s
build path, and `esbuild` is not added to `package.json` as a dependency (it ran via `npx` and is

Smoke-tested in real Chromium with no import map and no `node_modules` present at request time
(only the one bundle file plus `<script type="module">` referencing it): composer mounted,
`data-language="markdown"`, heading/bold/italic highlighted, mention chip intact. The transient
test page and DOM capture used for that check were not committed (not a deliverable of this spike;
`browser-dump.html` above is the recorded proof artifact for the unbundled path).

**Does the trim change which hosting option is cheapest? No — reported plainly, per the Owner's
condition.** The package count more than halves (52→26) and the import map shrinks by about half
(51→24 generated / 52→25 live), but it does not fall to "trivial": the live map still needed a
hand-added entry (`@marijn/find-cluster-break`) this run, the same fragility class Finding #6 in
the original spike already named — trimming the language list narrows the manifest, it does not
remove the class of defect. More importantly, the mandatory cost identified in the original
Decision answer — the current WebView2 host (`NavigateToString`) cannot serve import-map ES
modules at all, so *some* host change is required before R15 ships — is a hosting-integration fact,
untouched by which or how many CodeMirror packages are installed; the trim does not reach it. The
vendored-bundle option's structural advantages (one file, zero import-map maintenance, one HTTP
request instead of ~25) hold regardless of package count and are undiminished by the trim; if
anything the trim modestly *sharpens* the case for the import-map path (option a/b) by shrinking
its manifest and its maintenance surface, without closing the gap to option (c)'s zero-maintenance
property. **Conclusion:** the new numbers change the *inputs* to the Owner's plan (smaller install,
smaller manifest) but do not by themselves flip which option is cheapest — that still turns on the
WebView2 host-change cost and the import-map maintenance cost over time, neither of which this
measurement altered.

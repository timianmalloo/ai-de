Addendum B — Prompt Templates

amends spec v1.0 + Addendum A date 2026-09-10 status normative

Sessions become conversations of n prompts, and each prompt can be free-form or structured. This addendum specifies a template system for the composer: a versioned, extensible catalog of prompt templates tuned for high-reasoning models — each carrying when-to-use and why-it-exists guidance surfaced at pick time — three entry scenarios (blank, catalog-first, apply-template-to-free-form), per-block switching between shapes, and the assist provider — the configured model account (Claude default, Microsoft enterprise, or OpenAI) that powers template transformation and drafting help inside the tool itself.

B1Design principles (why templates, for these models)

  • Goals over scripts. High-reasoning models (Fable/Opus-class and peers) perform best when handed an objective, a rubric, and a boundary — not a step list. Templates encode ends + latitude: goal, done-when, constraints-as-invariants, evidence standard, budget, authority order.
  • Structure is for the reader too. The Owner and conductor consume prompts; a ruling request with options-costs-recommendation is answerable in one pass, prose ramble is not. Templates tune the Owner/conductor conversation, not just the human's typing.
  • Templates are artifacts. Versioned files, pack-distributed, projected deterministically to prompt text — the same doctrine as diagrams and session projections. Never a UI-only construct.
  • Free-form is never punished. Scenario 1 (this-chat-style prose) is a first-class shape forever; templates are an offer, and the apply-template transform makes structure reachable after thinking out loud.

B2The three scenarios

#ScenarioFlow
S1Blank, free-formNew Session with no template. Composer opens in Free-form shape; the person writes and sends exactly as in a chat. The conductor's Stage-0 triage handles tiering. Nothing about A5 changes.
S2Catalog-firstThe person picks a template (from the New Session sheet's optional "start from template", the composer's shape control, or /template). The editor becomes the template's structured form: typed fields, required markers, inline guidance, mention chips inside fields. Send is gated on validation.
S3Apply templateThe person writes free-form, then chooses Apply template (specific template, or "suggest one"). The assist provider maps the prose into the template's fields — exactly the "turn this into the right prompt" move from a chat with a strong model — and presents the filled form for review. Unmapped prose lands in the template's context field; missing required fields are flagged, never invented. The original draft is retained; "back to free form" restores it.

Per-block freedom: within one session, every block independently chooses its shape. S1 → S2 → S3 → S1 across successive prompts is normal use, not an edge case. Shape is recorded per block and visible as a badge in the Score outline.

B3The template model

B3.1 File format

A template is one markdown file with typed frontmatter and a body containing slots. Deterministic compile: template(version) + values → prompt text; the block's context recipe records template_id + version + values + assist provenance, so restart re-renders per spec §7.3 (against the current template version by default, with a diff shown; pinnable).

# ruling-request.template.md (excerpt)
---
id: ruling-request        version: 3        intent: decision
audience: owner           tier_default: T0
when_to_use: "A judgment call is blocking progress and the options are known."
why: "Rulings that can be answered in one pass need options, costs, and a
      recommendation up front; a prose request makes the Owner reconstruct
      the decision before making it."
fields:
  - { name: question,        type: text,    required: true,
      hint: "One decidable question. If two, file two." }
  - { name: options,         type: list,    required: true, min: 2,
      hint: "Each with cost/consequence. Include do-nothing when honest." }
  - { name: recommendation,  type: text,    required: true }
  - { name: evidence,        type: mentions, required: false }
  - { name: decides_by,      type: text,    required: false,
      hint: "What makes this urgent, if anything." }
---
A ruling is requested. Authority: your decision counts as the user's (CT20).
Question: {{question}}
Options and costs:
{{#options}}- {{.}}{{/options}}
Recommendation and reasoning: {{recommendation}}
Evidence: {{evidence}}
Record your ruling with rationale; it will be filed as a decision note and audit entry.

Common spine across all twelve: an objective (goal/question), done-when or output contract, constraints as invariants, authority/source-of-truth order, evidence standard, and budget/stop semantics. Template authors get this spine as the scaffold for new templates — and when_to_use and why are required metadata on every template, catalog-wide: a template that cannot say when to pick it and why it earns its place does not load.

B5The assist provider

B5.1 Requirement and configuration

AI-DE requires at least one configured account from: Anthropic (Claude) — default, Microsoft enterprise (Copilot), or OpenAI (ChatGPT). First-run onboarding gates New Session on one of the three reaching ready; the chosen one becomes the assist provider. Configured in Settings → Providers (and visible on the New Session sheet); one assist provider is active at a time; switching is a settings change, recorded as a session event when it happens mid-session.

# providers.yaml addition
assist:
  provider: anthropic          # anthropic (default) | microsoft | openai
  account: max-personal
  # resolves to a one-shot governed call through the subscription engine:
  # anthropic → claude-code · microsoft → copilot · openai → codex

B5.2 What assist does — and is not

  • Actions: apply-template (S3), suggest-template (rank 2–3 candidates for a draft, with one-line why), promote-to-goal-block (Addendum A's action, now assist-powered and re-based on the goal-block template), field-level help ("draft done-when from this goal").
  • Mechanics: a one-shot call through the assist provider's subscription engine (the same plane as lanes — no separate API path; the §4.2 invariant holds). No worktree, no episode ceremony: assist calls are not runs. They are evented (assist.request/assist.result with cost) so the profiler can attribute their spend to the session.
  • Discipline: assist maps and rephrases; it never invents required-field content — a field it cannot ground in the draft is left empty and flagged. The transform shows provenance (which prose fed which field) so review is a glance, not a re-read. The person's original draft is always retained and restorable.

B7Extensibility and authoring

The catalog is designed to grow. New templates are a file drop, not a release: anything valid under the pinned schema loads from any source in B3.2. The contract that makes growth safe:

  • Pinned schema. The frontmatter contract is template-schema/1 (id, version, intent, audience, when_to_use, why, fields with types/required/hints, body slots). Evolution is additive within schema 1 — unknown fields are preserved, never rejected; a breaking change means template-schema/2 with side-by-side load support, the same discipline as loomkeeper/1 and weave/1.
  • Load-time validation. A template that fails validation (missing when/why, unknown field type, bad slot reference, id collision within a source) does not load; the catalog view lists it with its errors instead of silently dropping it.
  • Three authoring paths. (1) Save-as-copy from any read-only template into workspace/personal (B3.2). (2) New template (/new-template and a catalog-view action): scaffolds the B4 common spine with empty when/why that must be authored before first save. (3) Create template from prompt — the inverse of apply-template: point the assist at a free-form prompt that worked (this run's launch prompt, a good investigation ask) and it drafts a template — fields inferred, the prompt's specifics demoted to sample values, when/why drafted for review. Provenance is retained; the draft is a proposal, never auto-saved.
  • Promotion path. Personal → workspace (commit alongside the code it serves) → pack (contribution to ai-forward, arriving everywhere via /updatepack). Templates follow the same artifact discipline as skills: born local, promoted on merit, versioned centrally once shared.
  • Anti-sprawl guard. On save, the catalog compares the new template's when_to_use against existing entries (assist-scored similarity); a near-duplicate prompts "extend that one instead?" — offered, not enforced. A catalog whose tooltips all sound alike has stopped helping people choose.

B8Requirements (extend spec §11)

R18Template engine and catalogP0

Files, sources, precedence, compile.

  • Templates load from built-in, pack, workspace, and personal sources with documented precedence; an override is visibly badged; the twelve B4 templates ship built-in with their when-to-use and why-it-exists text.
  • when_to_use and why are required by template-schema/1; a template missing either fails load with a visible catalog error; the picker renders when-to-use as the tooltip headline and why as its detail.
  • Compile is deterministic: same template version + values → byte-identical prompt text; the block recipe records template_id, version, values, and assist provenance.
  • Goal-block is re-based as template goal-block with zero behavior change to A5/R15 gating (regression-tested).
R19Composer shapes and per-block switchingP0

S1 and S2, and movement between them.

  • Blank session opens Free-form; sending prose works with no template anywhere in the path (S1 regression guard).
  • Template picker renders any catalog template as a validated form; a required-field gap blocks send with a field-level error; view-compiled shows the exact outgoing text.
  • Shape switches preserve content in both directions; each block's shape and values persist and restore; shape badges render in the Score outline.
R20Apply template (S3)P1

The assist transform.

  • Apply-template on a free-form draft produces a filled form with per-field provenance; ungrounded required fields are left empty and flagged, never fabricated.
  • Suggest-template returns ranked candidates with a one-line rationale each, grounded in the candidate's when_to_use text; the original draft is retained and restorable throughout.
  • Assist calls route through the configured provider's subscription engine, emit assist.* events with cost, and appear in the session's spend.
R21Assist provider configurationP0

The account gate and the default.

  • First-run onboarding requires one ready account among anthropic / microsoft / openai before New Session enables; anthropic is the pre-selected default.
  • Settings → Providers selects the assist provider; the New Session sheet displays it with live health; a mid-session switch emits a session event and applies to subsequent assist calls only.
  • No assist path exists outside the subscription engines (spec §4.2 invariant verified by test).
R22Template lifecycle in sessionsP1

Restart, versioning, catalog view.

  • Restart-from-block re-renders against the current template version with a visible diff when it changed; pinning to the recorded version is one click.
  • The catalog canvas view browses by intent, previews compiled output with sample values, shows Source via the shared editor, and save-as-copy promotes read-only templates into workspace/personal.
  • /updatepack refreshing pack templates surfaces as a catalog change notice, not a silent swap.
R23Template cohort on the boardP2

Close the loop.

  • Episodes born from a templated block carry template_id@version as a cohort attribute; the leaderboard's cohort lenses can slice by it — which prompt shapes produce better Weave outcomes becomes a query, same loop as model routing.
R24Template authoring and schemaP1

The catalog grows safely.

  • template-schema/1 is pinned and documented; unknown frontmatter fields are preserved; a schema-invalid template surfaces in the catalog view with its errors rather than silently dropping.
  • /new-template scaffolds the common spine and blocks first save until when-to-use and why are authored; save-as-copy promotes any read-only template into workspace/personal.
  • Create-template-from-prompt drafts a schema-valid template from a free-form prompt (fields inferred, specifics demoted to sample values, when/why drafted) as a reviewable proposal with provenance — never auto-saved.
  • Near-duplicate detection on save compares when_to_use against the catalog and offers (not enforces) extending the existing template.

Phasing: R18, R19, R21 join Phase 1 (the composer is being built there; goal-block-as-template must land before more shapes accrete, and the account gate is front-door work). R20, R22, and R24 join Phase 3 beside artifacts and sessions-store depth. R23 joins Phase 4 with the scoring lenses.

From a sketch to a workbench, with the method written down

AI-DE was specified, argued with, and built by running the AI-Forward pack as the engineering process. This page is the route through that month: the prompts that changed direction, the skill that answered each one, and the file you can open to see the result.

It is a reading of the audit and change ledger, not a transcript. The committed log holds 796 audit entries and 155 change entries. 132 of the audit entries are prompts, and 71 of those strings are distinct. One sentence accounts for 32 of the August prompt entries. September is the other shape: 54 prompt entries, 49 distinct texts.

The intention

The originating sketch, working name Atlas, states the product in one place.

Code is transient; the models are the product. Everything visual is a derived view over one graph, never hand-drawn. The shell is a thin host. Cross-session context flows through the graph, exposed to agents via MCP.

That paragraph is from the seed sketch. The product specification keeps the boundary and drops the parts the research could not support. The public site says the same thesis in the form meant for a visitor: the repository is the model, and code is one surface over it.

The repository README still describes an earlier object: a small WPF starter for spec-first, test-first agent experiments. The specification, the architecture, and the site describe the product that was actually pursued. Both documents are in the tree. They are not the same claim.

Install the method first

The first ledger line, 23 August, is addpacktorepo. The pack goes in before the product has a daemon, a store, or a terminal. The next line is adopt. Its summary records a public repository, a source-backed architecture of the starter, a four-term glossary, and a Docs Explorer. It also names an adoption proof. The proof file and the glossary file are not in commit 88e0c33f. What that bootstrap recovered, and what the next two days then rewrote, is the architecture.

The order is the approach. The agent does not invent a process beside the repository. The process is installed into the repository, and from then on the ledger is how a later session finds out what happened.

Research that changed the sketch

The same evening, collectknowledge built a sourced knowledge base. The ledger summary names four findings that invalidate assumptions in the sketch. Three of them are visible in the knowledge hub’s own framing and in the specification’s evidence section: the graph database named in the sketch had been archived, the MCP version under consideration was stateless, and a coordination lease without a fencing token is advice rather than mutual exclusion.

The specification records those as constraints, with the grounding path written at the top of docs/specs/ai-native-ide.md. The knowledge base itself is docs/knowledge/index.md. Fifteen topic indexes are in that tree now. The first run’s summary said ten topics and 71 artifacts. Later runs added WPF styling, operational dashboards, graph experience, editor surfaces, and the comparables for the solution tree. Research was not a preface. It was re-opened when a new surface needed comparables.

The specification

On 24 August, specify produced the product specification, an HTML reader of the same document, a privacy review, and an execution plan. The change log titles it “Specify AI-native IDE product boundary and user experience”.

Open the rendered specification or the markdown. The boundary that matters for everything after it is already in the evidence section: views are derived, relationships carry provenance, and coordination claims are not locks. The privacy review is a sibling of the spec, not a follow-up someone might remember to write.

An architecture that failed its review

On 25 August, define-architecture merged the specification and wrote the architecture, seven ADRs, the conceptual model, and the threat, privacy, and release plans. The next morning the operator did not accept it.

step back / /define-architecture ai-ide-arch-v2 — use the spec, the original architecture.md and your findings as input; redo the architecture to meet your bar

That prompt is in the ledger twice, as al-0007 and al-0196. The rerun summary says the 25 August draft was superseded: three spikes made re-runnable, ADR-0008 through ADR-0011, a write-ahead dispatch receipt, an in-process-first daemon, and an MCP egress binding. It records three hard vetoes and two soft vetoes closed. The document that carries the result is docs/architecture.md, which still says the baseline starter had none of those components, and that the architecture is the target shape.

The habit is in the prompt, not in the skill name. “Step back” means the previous artifact is input, and the skill runs again against a bar the operator is willing to say was missed.

A walking skeleton the same day

The v2 architecture, the Phase-1 design, and the Phase-1 implementation are three ledger lines on 26 August, between 00:36Z and 01:10Z. design wrote the grains, the contracts, and the failure modes. implement built the walking skeleton red-first: a SQLite fact store, the write-ahead two-phase dispatch, a fixture extractor, and bounded projections.

The design is phase-1-walking-skeleton.md. The proof pack is phase-1-proof-pack.md. The store decision is ADR-0002. The dispatch receipt is ADR-0010.

A benchmark entry the same morning, al-0011, records that the first run failed 5 of 8 budgets because a projection materialized the corpus, and that pushing the filter into SQL changed the describe query by 69×. That number is the ledger’s record of the run. It was not re-measured for this page. The write-up is phase-1-perf-results.md.

The workbench, from one sentence

The same afternoon, one prompt named the missing product behavior and named the three skills to run.

the tooling should allow resize of panes and docking of elements like eclipse or vs code or photoshop/premiere. step back and make sure this is part of the spec. Consider exemplars in multi-pane, resize, hide, dock, move. /specify these capabilities, then /ui-design, then /define-architecture

At 13:39Z the ledger has three entries with the same summary: specify, ui-design, and define-architecture. The spec gained the exemplar matrix. The mockup is below. The docking decision is ADR-0012, and layout persistence is ADR-0013.

Implementation followed as a series of small implement entries the same day: a headless layout model, an AvalonDock adapter, a keyboard command catalog, drop targets, the shell, and the command palette. A spike found that a version field on the layout envelope had no migration, so the first rename of a surface would have reset every saved layout. That is the pack’s spike protocol used as a tripwire during implementation, not as a research phase that had already closed.

Spikes allowed to veto the plan

Component 1 of the extraction plan depended on the compiler hosting the repository’s own build. A spike recorded that a real solution loads, and that repository-authored generator code executes inside the extractor’s process. The change log then says, in two titles: the spike blocks Component 1, and the adopted strategy is that extraction never runs repository code.

The spike write-up is spikes/roslyn-msbuild-workspace/RESULT.md. The architecture change is the 28 August entry “Component 1 adopts Strategy 1”. The pattern is the same as the architecture rerun. Evidence is allowed to retire a component that the plan was fond of.

Other spikes in that week chose a terminal renderer, kept WebView2 for the canvas and handled overlap by snapshot swap, and later froze WPF TreeView for the solution tree only after a read-and-run probe. Results live under spikes/ and docs/spikes/d0-tree-toolkit/.

The product as the instrument

From 28 August the prompts change register. They are no longer “write the spec”. They are what the operator saw while using the build.

One list starts with illegible menu type, dead icons, and a default layout: console on the bottom, workspace on the left, graph and domain on the right. Another, pointed at a real repository called TheTerrace, says the tool is showing two nodes where Obsidian shows a graph. A later one says the knowledge count is zero while the code count is large, and then states the rule the operator wants enforced:

do not infer… the graph should only be on observable links/relationships

Those prompts become investigations and change-log titles rather than a fresh specification. “The graph surface had never shown a graph: two nodes of 2,813.” “INV-0003: the graph could not fit through the pipe.” “Knowledge was zero because nothing ever looked.” The write-ups are INV-0003 and INV-0004.

This is the coding approach in practice. The specification stays authoritative for what the product is. The running build is the instrument that finds where the specification is not yet true. The operator’s phrasing is allowed to become a constraint — “do not infer” — and the change log records the constraint as an architecture decision: a matcher that invents facts is worse than one that misses them.

Two sessions, one contract

On 29 August the work stopped fitting in one session. The prompt assigns the split out loud.

there are two sessions working in two different worktrees your sessions need to be collaborative with each other one session, the claude code session, will work on the core capabilities

The same day a prompt points out that a session had written into the primary checkout, names the worktree rule, and tells that session to correct it. The change log records “A written contract between the core and design sessions”. The register that contract became is docs/collaboration/session-contracts.md.

adddomainexperts ran once, adding three domain lenses — graph visualization, WPF styling, UML and ERM modelling — and docs/domain-experts.md. The mockups that followed are part of the same split: the design session could see a facelift, a knowledge explorer, and UML/ERM surfaces while the core session kept extracting. app-facelift.html, knowledge-explorer.html, uml-erm-surfaces.html.

Loomkeeper

At the end of August the second idea in the site’s thesis gets its own specification: an agentic watcher that scores collaboration on evidence. The change log on 30 August says “Specify Loomkeeper and the Weave Score authority split”, and the design entry the same day says the observatory direction was adopted.

The spec is agentic-watcher-substrate.md (rendered). The architecture is architecture/loomkeeper.md. The plan that scheduled the work is plans/agentic-watcher-substrate.md, an optimize-graph artifact. Implementation then shows up as numbered slices in the change log: an append-only observation store, an ingest wire, a sessions surface, a work-episode vocabulary shared with the pack’s goal state, a message board, a dispute that appends a fact instead of overwriting a score.

The daydream — the online half of “what keeps recurring becomes a lesson” — is specified and, in the map of content’s own words, not built. That sentence is left standing in docs/index.md. A 3 September prompt says “Core reported the Not-Scored prediction refuted; verify independently and act on it.” The approach is to distrust a green story from the other session until it has been checked.

A design that stopped

On 4 September design-slice for an MCP path stopped at grounding. The ledger says ADR-0011 bound MCP authorization to a session processing class, and the session model had no such field. The skill’s instruction in that situation is to stop and write the gap down, which is what the entry records. The note is note-20260903-the-control-under-mcp-has-no-input.md.

A later design, mcp-enlightened-path.md, is the slice that did proceed. Its summary says the slice adds no durable state, because the board post already appends the same ledger the humans use. Stopping is part of the method. So is the next design being smaller than the one that could not be grounded.

Perspectives and the compile step

By 11 September the operator is using a build and refusing the information architecture.

I think the experience is very cluttered (rapidly) because it is mixing use cases in a common set of docks. We need to clean up and refactor the entire user experience and tighten up what can be done where and when.

That prompt is the start of Addendum C. Use cases become perspectives: a session is the primary object for agentic coding, and the docks are no longer a single shared junk drawer. The same day, a separate line of prompts decides that tier should fall out of compiling the prompt, and then enumerates the contexts a compile needs: model family, conversation, repository standards. The operator accepts Addendum D, the compile step as its own bounded context.

The specs are addendum-c-perspectives.md and addendum-d-compile-step.md. The architecture block is ADR-0030 through ADR-0037, linked from docs/architecture.md. The coordination plan that split the build into lanes is addendum-cd.md (HTML).

Prompts over the next two days are operator notes from the build: the composer fields were squeezed into a short region, contrast failed, a session should take the whole window, budgets should default to the subscription rather than a cap the operator has to invent, and a first-use machine with no agent backend had been missed. The mockups that absorb those notes include conversation-composer.html, perspective-shell.html, session-front-door.html, and first-use-accounts.html. Screenshot folders named in the prompts stay on the operator’s machine. They were not copied into the repository. The mockups and the ADRs are the durable copy.

A fleet, then a wind-down

execute-with-coordination is the second-largest skill in the ledger, 93 entries, almost all of them in September. prepare-for-coordination wrote the lane plan. The prompts name the roles the operator wanted in the room: an Owner, a Conductor, sub-agents in their own worktrees, and a watcher on another harness. One prompt says the Conductor should not block on the human to land a fix. Another says to kick the other sessions so the work keeps moving.

The join entries are the readable layer. al-01M2BHJNQVJ1P3K02B0FD0JRE1 records CV-1 and X-2 merged. al-01M2V19J6D5PFZVEADASW69P7P records main green on 18 September and says the branch had been red since 12 September. That is the ledger’s account of a CI run. This page did not re-query the run.

The last operator prompt in the committed log is the stop.

we need to wind down this work gracefully end sessions and mark complete and todo so we can pick up in the future relinquish the watcher role clean up outstanding worktrees and get main to clean and up to date

The resume map is session-winddown-2026-09-18.md. It separates finished evidence from unfinished delivery and says the handoff does not re-arm implementation. The fleet is part of the method, and so is an explicit end. “Keep going” is a real prompt in this log. It is not the last word.

How the prompts were actually used

The 71 distinct prompt strings are not 71 ideas. The histogram of the 132 entries is 50 strings once, 16 twice, three strings four times, one string six times, and one string 32 times.

The 32-count sentence, all of it inside the August block, is:

do the next steps you have listed provide the standard status and next steps tables afterwards

August holds 78 prompt entries and only 22 distinct strings. A large share of that month is a cadence: the agent proposes the next steps, the operator says to do them, and the status comes back as a table. Alongside it, four entries say to commit, push, merge, and leave main clean so the operator can test the build while the session continues. September holds 54 prompt entries and 49 distinct strings. “do next steps” appears four times. Almost everything else is a specific steer: a defect seen in the client, a role assignment, a ruling, or a stop.

Some August prompts are stored twice, under two id sequences, and at least one pair differs by a damaged dash character. Seventy-one is a count of strings in the file. It is an upper bound on the number of distinct asks, not a count of decisions.

Read that way, the approach has five moves.

  1. Install the pack, then talk to it by skill name. The directional prompts say /specify, /ui-design, /define-architecture, /investigate. The skill is the unit of work.
  2. Send the previous artifact back in. “Step back” plus the path of the thing that missed the bar. The architecture v2 run is the clearest case.
  3. Once a plan exists, run the cadence. The repeated sentence is the operator refusing to re-derive the plan every turn, and refusing to accept a turn that does not end in a status table.
  4. Use the product, and let that replace speculation. Menu contrast, two graph nodes, a blank composer, zombie terminal hosts, a machine with no agent backend. Several of those became investigations with numbers in the filename.
  5. Split sessions on purpose, and end them on purpose. A written contract, an owner and a conductor, worktrees, and then a wind-down that marks what is done and what is only a resume pin.
